# UI language (i18n)

> Related: [features](../features/i18n.md) · ADR-0013 (language set and scope boundary) · ADR-0014 (self-built typed i18n layer) · ADR-0015 (structured IPC errors)

## Problem Statement

Every piece of UI copy is hard-coded in Simplified Chinese in the source, so a non-Chinese user
opening the app cannot read a single heading, button, empty state or error notice. The copy is
scattered across the renderer's JSX, errors thrown by the main process, and hand-written date and
number formatting, and no layer of it is replaceable.

## Solution

Support six UI languages plus "follow system" as **the default option**. The user can switch at any
time from the settings page, and a switch applies to the whole app immediately, with no restart and
no save.

"Follow system" is **a policy, not a snapshot**: while it is selected, the UI follows the macOS
preferred languages, using English when the system language is not supported; choosing a specific
language locks it, and later system language changes no longer affect the UI until the user actively
selects "follow system" again.

Failure information crossing process boundaries becomes a structured form containing no natural
language, and the renderer produces the wording in the current language.

## User Stories

1. As a French user, I want the UI to be in French when I open the app, so that I do not have to
   understand a foreign language first just to find the language setting.
2. As someone whose system language is Korean, I want the UI to fall back to English rather than
   Chinese, so that I can at least read an international lingua franca.
3. As a Chinese user on an English system, I want to switch the UI back to Chinese by hand, so that
   the system language does not hold my application language hostage.
4. As a user of any language, I want to see every available language at a glance in settings, each
   written in its own script, so that I can recognise my own language even when the current UI is in
   one I cannot read.
5. As a user, I want each language's English name shown alongside it, so that when I cannot read the
   native script (having switched to Japanese by accident and wanting English back) I have a second
   clue.
6. As a user, I want the whole UI to change immediately on a language switch, including the sidebar
   tooltips and the application menu, so that no half-translated state is left behind.
7. As a keyboard user, I want to switch languages with Tab to focus, arrow keys to select, Enter to
   confirm and Esc to cancel, so that I do not have to use the mouse.
8. As a user, I want my language choice to still be there next time I open the app, so that I do not
   have to set it again every time.
9. As a user, I want failure notices in my language too, so that a foreign language does not appear
   at exactly the moment I most need to understand.
10. As a user, I want dates, times and numbers displayed by my language's conventions, so that I do
    not see American dates in a Chinese UI or Chinese weekday names in a Russian one.
11. As someone who switches system languages often, I want the UI to follow the system automatically
    when "follow system" is selected, so that I do not have to change it again in the app every time.
12. As someone who always uses one language, I want later system language changes not to affect the
    app once I have chosen a specific language, so that my choice is not quietly overruled by the
    system settings.
13. As a user, I want to see which language "follow system" currently resolves to, so that I do not
    have to guess what that option actually does.
14. As someone who has already chosen a specific language, I want to be able to select "follow system"
    again, so that the decision is reversible rather than one-way.
15. As a developer, I want a missing translation to fail at compile time, so that I do not find out a
    UI is blank only when a user switches to that language.
16. As a developer, I want all six languages forced to be complete when adding a piece of copy, so
    that there is no "ship first, translate later" window.

## Failure modes and boundaries

### Startup and deciding the language

The language preference's value domain is `follow system | zh | en | fr | es | ru | ja`, defaulting to
`follow system`. "Resolution" in the table below happens only when the preference is "follow system".

| Scenario | Expected behaviour |
|---|---|
| First launch (preference = follow system), the first entry in the system's preferred language list is supported | Use that language |
| The first entry is unsupported but a later entry is supported (e.g. `[ko, fr, en]`) | Take **the first supported one** in list order, i.e. French. **Do not fall straight back to English just because the first entry missed** — this is the easiest line in this section to get wrong |
| No supported language anywhere in the list (e.g. `[ko]`) | English |
| The system returns tags with a region or script (`zh-Hans-CN`, `fr-CA`, `pt-BR`) | Match on the primary language subtag: `zh-Hans-CN` → Chinese, `fr-CA` → French; `pt-BR` does not match, so continue to the next entry |
| The system language API returns an empty array or throws | English, no crash |
| The preference is a specific language and differs from the system language | Use the preference's language. The system language **plays no part at all** in the resolution |
| The preference file's language field is an invalid value / the wrong type / has been deleted by hand | Degrade to "follow system" (the default value) and take the resolution path; the other preferences (colour scheme and appearance mode) are unaffected |
| The whole preference file is corrupt and unparseable | Every preference reverts to its default, so the language is "follow system". Consistent with the existing colour scheme's degradation behaviour |
| The first frame, before the preferences have been read | Must not render a default language first and then jump (FOUC). The language has to be decided before the first frame |

### The dynamics of "follow system"

| Scenario | Expected behaviour |
|---|---|
| The preference is "follow system" and the user changes the macOS preferred languages while the app is running | The UI should change with it. If it cannot be live, it must at least take effect on the next launch, and must never stay stuck in the old language incorrectly |
| The preference is a specific language and the user changes the macOS preferred languages | The UI **does not change**. Measured across every system language configuration |
| Switching from a specific language back to "follow system" | Re-resolve from the current system language and apply immediately, without keeping the previously locked language |
| The preference is "follow system" and the system language goes from supported to unsupported | Fall back to English rather than staying on the last resolved language |
| The two "follow system" settings, UI language and appearance mode, coexisting | They do not interfere: changing the system language affects only the language, changing the system appearance affects only light/dark. The two are structurally identical but independent preferences, see [appearance](appearance.md) sequence B |

### Switching languages

| Scenario | Expected behaviour |
|---|---|
| Switching to the currently selected option (including re-selecting "follow system") | A no-op, with no notice |
| The notice wording when "follow system" is selected | It must state the current resolution ("set to follow system · currently X"), not just "switched to follow system" — the user cannot tell which language that is |
| An asynchronous scan or load is in flight when the language is switched | The in-flight operation is not interrupted; its completion notice uses the **new** language |
| An error notice is on screen when the language is switched | That notice re-renders in the new language (errors are held as a code plus parameters, not as a finished sentence) |
| Writing the language to the preference file fails (full or read-only disk) | The UI language still switches (an optimistic update), with a separate failure notice explaining "in effect for this session, reverting on restart". Consistent with the existing handling of a failed colour scheme switch |
| Switching several times in rapid succession | The last one wins, with no intermediate language left behind |

### The dropdown selector

| Scenario | Expected behaviour |
|---|---|
| The settings page scrolls and the page is scrolled while the overlay is open | The overlay closes (the overlay is positioned outside the scroll container, and must never be left floating out of place) |
| The trigger is at the bottom of the viewport with insufficient space below | The overlay opens upwards and is not clipped by the viewport |
| Clicking elsewhere on the page while the overlay is open | Closes, selecting nothing |
| Pressing Esc while the overlay is open | Closes without changing the language, and focus returns to the trigger |
| Opening the overlay from the keyboard (↓ or Enter) | The highlight **stays on the currently selected item**, without moving an extra step because of the key that opened it |
| Continuing to press an arrow key past the first or last item | Cycles to the other end among the **seven** items (follow system + six languages). The divider takes no slot and cannot be focused |
| The secondary text of the "follow system" item | Shows the name of the currently resolved language, updating as the system language changes; it is not static copy |
| Highlighting an item from the keyboard and closing without pressing Enter | The language does not change (highlighting is not selecting) |
| The window is resized while the overlay is open | Repositions to the trigger rather than staying at its old coordinates |

### The copy itself

| Scenario | Expected behaviour |
|---|---|
| A language is missing a piece of copy | Fails at compile time, never reaching runtime |
| Copy still cannot be found at runtime (theoretically unreachable) | Fall back to English and warn; never render blank and never display the key name |
| Displaying a quantity in a language with several plural forms, such as Russian | Choose the word by that language's plural rules, with no "number + fixed measure word" concatenation. A language may instead sidestep agreement altogether with an invariant construction — Russian uses a genitive label (`вопросов: 5`), correct at every count — and that is equally acceptable; what is not acceptable is a hard-coded form. Where a numeral **is** inlined, the form set depends on the surrounding grammar, not just the count: after Russian `среди` the noun takes the genitive, giving a different set from the one that follows a bare numeral |
| A quantity of 0 | Each language follows its own rules (English uses the plural, French the singular), with no special-casing |
| A count next to a noun the source language marks with a counter word (`${n} 条`) | The counter is part of the meaning, not punctuation. Dropping it leaves a bare numeral, and two of these slots are `text-transform: uppercase`, where the numeral ends up between two unrelated words with nothing to say what it counts |
| A fixed-width container in a verbose language (French and Russian are longest for prose, Japanese for labels) | No truncation, no overflow **and no wrapping onto a second line**. See the measured note at the end of this document: the rows at risk here wrap rather than clip, so an overflow check does not detect the failure |
| Punctuation that belongs to the language (quotation marks around a session title) | Comes from the dictionary, never hard-coded in a component. English `“ ”`, French `« »` and Japanese `『 』` are copy, and the same title must be quoted the same way everywhere it appears in one language |
| The UI language differing from the content language (browsing a Chinese session in a French UI) | Content displays as written and is not translated; only the surrounding UI changes with the language |

### Number and time formats

| Scenario | Expected behaviour |
|---|---|
| Relative times (today / yesterday / N days ago) | Expressed in the current language, with no hard-coded Chinese words |
| Weekday and month names | In the current language, not from a hard-coded Chinese array |
| Large number grouping separators (1,234 / 1 234 / 1.234) | Follow the current language, with no single locale hard-coded |
| A value of NaN / Infinity / negative | Do not throw and do not display "NaN"; give a stable degraded representation |
| Byte sizes and durations | The number is formatted by language; the unit symbols (KB / MB / ms) are not translated |

### What imported content can do

i18n adds no new content render sites of its own, but it changes existing render sites' **content
sources**, so each needs its boundary drawn:

- **Error parameter interpolation**: a structured error's parameters (paths, filenames, indices) come
  from the filesystem and user data, and splicing them into wording must go through the same escaping
  as the existing rendering — not bypassed on the grounds that "this is our own error copy".
- **Displaying language names**: the six language names are fixed constants, do not come from external
  input, and are not an injection surface.
- **The application menu**: menu item copy comes from the i18n dictionaries (fixed constants). The menu
  is a native main-process control and does not accept arbitrary strings passed in from the renderer.
- **Existing content render sites (sessions, memories, artifacts) are outside this change surface**:
  they render agent-generated content, whose link destinations and sanitising boundaries are already
  constrained by existing invariants, and i18n neither relaxes nor tightens them.

## Implementation Decisions

### The shape of the i18n layer (see ADR-0014)

- Simplified Chinese is the source language and the single source of truth. The other five align to it
  **entry by entry** in the type system, and one missing entry fails typecheck.
- `as const` on the source language narrows the values to literal types, so the other languages cannot
  reuse that type directly; a type mapping is needed that widens leaf values to `string` while
  preserving the completeness of the key set. **That type gymnastics is why ADR-0014 was in the
  "Proposed" state**; implementation verified it first and promoted it to "Accepted" once verified.
- Copy carrying a quantity or an interpolation is expressed as a **function** (parameters in, string
  out), not as a template string concatenated at the call site.
- Plurals call the platform's built-in `Intl.PluralRules` rather than a hand-rolled rule table. `plural()`
  lives in its own leaf module (`src/shared/i18n/plural.ts`) rather than in `index.ts`: `index.ts` imports
  every dictionary, so a dictionary importing `plural` back from it becomes circular and can then only be
  loaded through `index.ts` — a property invisible at the call site and unenforced by the type checker.
  `plural()` takes the bare language code as its locale tag, because reading each dictionary's `htmlLang`
  would reintroduce that import; CLDR keys plural rules off the primary subtag, so the two agree, and a
  test asserts that agreement across the whole language set rather than leaving it to hold by luck.
- The copy layer is pure data plus pure functions with no React dependency, shared by the main process
  and the renderer.

### Language preference and effective language (two concepts, not to be merged)

- **The language preference** is the persisted user choice, valued `follow system | one of the six`,
  defaulting to "follow system".
- **The effective language** is the language the UI is actually using right now, always one of the six,
  derived from the preference: a specific preference is taken as is, and "follow system" resolves the
  system language.
- The two **must not be merged into one field**. Storing the resolution directly into the preference
  would degrade "follow system" into a one-off snapshot — the user changes the system language and the
  app stays on the language resolved back then, with no way left to distinguish "they chose follow
  system" from "they chose that language by hand".

### Language resolution

- The system language comes from `app.getPreferredSystemLanguages()` (which returns a **list** in
  priority order). **Not** `getLocale()` / `getSystemLocale()` — Electron 43's type definitions state
  in both of their docs that the former is what to use for the user's language; the latter two describe
  the regional format (numbers/dates/currency), which is not the same thing as language.
- Matching rule: iterate the list, compare each entry's primary language subtag against the supported
  set, and the first hit wins; fall back to English if none hit. **Iterate the whole list**, not just
  the first entry.
- Resolution is a pure function (language list → effective language), decoupled from preference
  storage, which makes all of the boundaries above unit-testable.
- The language must be decided before the window's content renders, to avoid a first-frame language
  jump.

### The main process emits no natural language (see ADR-0016)

- The constraint widens from "failures crossing IPC" to "all user-facing natural language crossing
  IPC": placeholder and degraded text, truncation markers, advisory copy, quantifiers in configuration
  summaries, and the language-varying entries in display-name tables all become structured signals sent
  by the main process (a code + parameters / `null` / a boolean / a count), with all sentence
  composition happening in the renderer.
- The criterion is executable: run a whole-repository Chinese literal search over `src/main`,
  `src/shared` and `src/preload` (**with `grep -a`**, since `token-stats.ts` contains NUL bytes and
  plain grep silently skips it), and what remains should be only developer logs that **never reach the
  UI** (`console.*`).
- This adds two shared shapes: `CappedText` (text + whether it was truncated) and `AppError` on data
  fields. **"No value here" and "the value is legitimately an empty string" must be distinguished in
  the types**, or the renderer's `?? placeholder` will clobber a legitimate empty value.

### Structured errors (see ADR-0015)

- Failures crossing IPC travel as an error code plus parameters, containing no natural language. The
  error code enum and the parameter types live in the shared layer, imported from there by both the
  main process and the renderer (following ADR-0001's single type source convention, growing the three
  shared pieces to four).
- **The carrier format (settled by measurement in ticket 05, 2026-08-09)**: the code and parameters are
  **serialised into the Error's message** behind a fixed marker prefix, and decoding locates the
  payload by that marker in the string. Both more natural approaches are **unworkable** — when an Error
  crosses IPC in Electron its custom properties are all lost (only `message` / `stack` survive), so
  `e.code = …` never reaches the other side; and the message is wrapped in an
  `Error invoking remote method '…': Error: …` prefix, so `JSON.parse(message)` cannot extract it
  either. When the payload cannot be decoded, always **degrade to displaying it as is** (without
  throwing), which serves both the migration period's coexistence and avoids "erroring while
  reporting an error".
- **Error parameters may only take language-independent values**: identifiers (channel names, field
  names), paths and numbers. Never finished wording — that is precisely what this protocol exists to
  eliminate.
- **Unknown error codes are not passed through**: decoding validates that the code is in the enum, and
  anything else is displayed as an old-style error as is. Passing it through would leave the renderer
  with no wording and a blank display, and blank is worse than one ugly line of original text.
- **The renderer keeps a "display as is if it will not decode" fallback, and it is permanent** (settled
  in ticket 06 on 2026-08-09, confirmed by the user). Since the protocol closed there is no
  **cross-process producer** left taking that path (confirmed by a whole-repository search: zero
  `throw new Error` in `src/` outside tests, and no whole-sentence message on any contract field), but
  its entry points are not limited to IPC — the renderer's own TypeErrors and anything a third-party
  library throws **will never have an error code**. So this branch's character changes from
  "compatibility with the old protocol during migration" to "**the last display guarantee for
  non-protocol exceptions**", and it stays. The acceptance criterion for closing the protocol changes
  accordingly: not "this code is gone", but **no Chinese whole-sentence error crossing a process
  boundary anywhere in the repository** — the former is unreachable and harmful, the latter is
  searchable and re-checkable.
- **A new error code must come with its wording, guaranteed by typecheck**: the code → wording dispatch
  is a switch with a `never` assertion at the end, so an unhandled code fails compilation (verified by
  mutation: adding an unhandled code reports TS2345).
- Branching on error semantics is done on the error code. **The one existing branch matching a Chinese
  substring must be changed as part of this**, or a wording change would make it fail silently with no
  test going red. That site is `errLabel` in `SubagentsView.tsx` (ADR-0015 originally recorded it as
  `MemoryView.tsx:91`; the filename was wrong and has been corrected). It reads a **data field** rather
  than a thrown error, so the fix is to give that field a language-independent failure category
  (`errorKind`) and branch on the category; the Chinese detail already in the field is data-field
  display copy and belongs to ticket 07.
- **The renderer gets the current language from context** (landed in ticket 05, 2026-08-09): error
  render sites are scattered across the session page, the plugin list and the skill expansion blocks,
  so passing it down as a prop would have to thread through intermediate components with no stake in
  it; and the spec requires an on-screen error to **re-render** in the new language, which a
  module-level variable cannot do since changing it triggers no re-render. So errors are held as a code
  plus parameters and composed into sentences at render time.
- The contract validation layer's failure reasons are included too, with no source-language text
  retained.

### Preference persistence

- Language is one of the app's own preferences alongside the colour scheme, reusing the existing
  preference storage with its atomic write and three-tier degradation strategy.
- What is persisted is **the preference** (including the `follow system` value), not the resolved
  effective language.
- The existing preference storage's interface has the shape "one setter per preference"; adding
  language extends that interface.
- An invalid single preference degrades only itself and does not affect the others (following the
  existing "degradation may only hurt itself" invariant).

### The application menu

- There is currently no custom menu, so Electron's default menu is used (localised by system
  language). This round builds a custom menu whose copy comes from i18n and follows the in-app
  language.
- The structure follows the standard macOS menu set, plus two keyboard entry points to existing
  features (settings, global refresh).
- The menu has to be rebuilt after a language switch, not constructed once at startup.

### UI (conclusions; the form is in the prototype gate below)

- The settings page gains a "Language" section, **placed before "Appearance"** — it determines how the
  rest of the page reads.
- The selector's form is "label + dropdown trigger", opening into an overlay list of **seven** items:
  "follow system" first, a divider, then the six specific languages. The divider expresses that the two
  are different in kind — the former is a policy, the latter are values.
- Each item has its primary name on the left (a specific language written in its own script) and
  secondary text on the right, with the current item ticked and highlighted on the right. **The
  secondary text slot of "follow system" holds the currently resolved language name**, in the same slot
  where specific languages hold their English name, so the user can see at a glance what that option
  currently equals.
- With the preference on "follow system" the trigger shows both the policy name and the resolution
  (primary + secondary); with a specific language it shows only that language's native name.
- The overlay **must be positioned outside the settings page's scroll container**. Measured: the
  settings page container is `overflow: auto`, and an ordinary absolutely positioned element of the
  same size inside it gets clipped; after repositioning the overlay in viewport coordinates, hit tests
  at all four corners and the centre pass.
- The overlay's right edge aligns with the trigger's right edge, opening downwards by default and
  upwards when there is not enough space below.
- The new dropdown arrow and the selected tick use **inline SVG** (copied from Lucide's official
  internal elements), not characters. The existing character icons are outside this change surface and
  have been recorded in a separate ticket.
- The overlay's shadow needs a new theme variable, which must be given a value in all six variable
  blocks (3 schemes × light/dark), with a higher alpha in dark than in light to be visible.

### Existing shapes explicitly not changed

- The `Provider` and `TrendMode` types once used Chinese literals as runtime values (`'其他'`,
  `'合计'`) and have been **sanitised** into language-independent identifiers (`other` / `total`).
  **It has been verified that these two values were never persisted**: the usage archive's row
  structure stores only the raw model string, the token metering cache's entries likewise store only
  the raw model string (the provider is derived live from the model name every time), and they do not
  appear in the preference file either. So the rename has zero impact on existing user data.
- **Value and display name are separated**: after sanitisation, the UI text comes from a display-name
  constant table living in the same module as the values (the same form as the existing colour scheme
  label table). The three vendor names and Claude / Codex are proper nouns common to every language,
  so only `other` and `total` need to vary with the UI language.
- **`byProvider`'s weak key type is a known risk**: that field carries provider keys as
  `Record<string, …>`, so when the producer and the consumer disagree **typecheck does not report it**
  and the trend segmentation silently goes empty (the values and bar heights stay correct, only the
  segments disappear). The current defence is a warning comment in the producing module plus a
  pipeline test that builds keys with the producer's function and reads them through the consumer;
  tightening the key type so the type system takes over this consistency is on the refactor list,
  pending a decision.
- The search box's placeholder currently glues an icon character and copy into one string; i18n must
  split the icon out and leave it in the component, or the icon would be carried into six language
  dictionaries.

## Testing Decisions

A good test asserts only external behaviour: given a language and an input, what the copy layer
outputs; given a system language list, which language resolves; given an error code and parameters,
what renders. It does not assert the dictionaries' internal structure, nor which function a component
calls internally.

**Seam selection** (reuse the existing first, add as little as possible):

| Seam | Nature | Coverage |
|---|---|---|
| The copy layer (pure data + pure functions) | **New — this feature's only new seam** | Six-language key completeness, plural rules, interpolation escaping |
| Language resolution (a pure function) | New, at the same layer | Every matching and fallback branch of system language list → effective language; and the derivation of preference + system list → effective language (including "when the preference is a specific language the system list plays no part") |
| Preference storage | **Existing** | Reading and writing the language field, degradation on an invalid value |
| IPC contract validation | **Existing** | The shape of structured errors |
| e2e | **Existing** | Run the existing cases pinned to English (asserting zero behavioural changes); plus dedicated i18n cases |

**Existing precedent**: the current tests for preference storage and the colour scheme are not coupled
to any copy and can be copied straight across for language; the shared UI consistency check script
hangs off the verification gate and is a ready-made template for the new "copy completeness gate".

**e2e strategy** (see ADR-0013's decision background): about 127 locators and assertions in the
existing cases depend on UI copy, but what they guard is **behaviour** rather than copy, so they are not
rewritten when the pinned language changes. The approach is to seed the preferences so the tests pin one
language — the project already has a mature technique of per-case isolated `userData` with seeded files.
New dedicated cases cover: switching takes effect, all six languages load, and key layouts do not
overflow in the longest language.

**The pinned language is `en-US`** (changed from `zh-Hans-CN` by ADR-0017): with the repository's working
language now English, an English locator is readable to the same people who read the rest of the file.
The English strings come from `en.ts` by key rather than by translating the Chinese ones — a value→key
reverse lookup is unsafe, and measurably so: of 172 unique reverse mappings, `'返回'` resolved to
`'Output'` because the only leaf exactly equal to `'返回'` is a tool's *return value*, not the *back*
button. It was unique, just uniquely wrong.

**Two cases keep their non-English assertions on purpose**: the language selector case launches with
`zh-Hans-CN` and the menu case with Japanese, so the Chinese and Japanese copy they assert on *is the
thing under test*. A blanket replacement changed those too and the tests caught it.

**Gate**: a new check scans the source for Chinese literals not yet in the dictionaries, hooked into
the verification gate. Missing translations are caught by the type system and un-extracted copy by
this gate; the two do not overlap.

**A known test gap (no fake greens)**: the Electron application menu is a native macOS control and
Playwright cannot reach its rendered result. What is testable is **menu template construction** — a
pure function of "language → menu structure", unit tested on that seam for its copy and structure;
which language the menu actually displays, and whether it rebuilds after a switch, can only be
accepted by hand. "The build function returned French copy" must not be passed off as "the menu
displays in French".

### The error detection pattern changes with the protocol (added 2026-08-09)

Once structured errors landed, **smoke's and e2e's failure detection patterns had to change with
them**: they had been matching on the **Chinese wording** "契约校验失败", which no longer exists after
ticket 06 — so the pattern became a **dead pattern** that could never match anything again, silently
weakening the detection net with nothing to report it.

It now matches `agentshed-error:` (the marker common to every cross-process failure since ticket 05).
The coverage is wider than before: the old pattern was actually only held up by
`Error occurred in handler`, and **a form the main process catches internally and `console.error`s
itself, without that prefix, was its blind spot**; the new marker is unaffected by prefixes.

The generalised lesson: **any detection or branch that matches on wording fails silently when the way
that wording is produced changes** — which is exactly the coupling ADR-0015 exists to eliminate, and
it is harder to find hiding in the test infrastructure than in production code.

### The six READMEs' reachability is guaranteed by a gate (settled 2026-08-09)

"Any entry point can reach the other five" is a **decidable property** and is now baked into
`check:ui`: each README is verified to link to the other five, with exactly one bold entry in the
language switcher row (zero = the reader cannot tell which one they are on; more than one = a
copy-paste that missed an edit). Both directions were mutation-checked to go red. If a link is missed
when adding a language or renaming a file, the gate catches it — nothing else would flag that kind of
omission, and a reader only discovers it by clicking a dead link.

**An assumption the measurements overturned**: it was assumed Russian and French would be longest
everywhere; measurement showed the longest version of the "UI language" label is **Japanese**
(full-width characters), while French and Russian are longest for prose paragraphs. Both classes have
to be checked when rechecking fixed-width containers — the prose length alone is not a safe basis.

**A second assumption the measurements overturned (2026-08-09)**: over-long copy was assumed to burst
its container horizontally, and every obvious check for that is vacuous here —

- `.tabs` is width-auto, so its `scrollWidth` always equals its `clientWidth`;
- `body` is `overflow-x: hidden`, so `documentElement.scrollWidth > clientWidth` never fires;
- `.tab` is `white-space: normal` with `flex: 0 1 auto`, so an over-long label neither clips nor
  overflows its box.

What actually happens is that the label **wraps and the row grows vertically**: measured at 34px → 268px
for the tab row, and 98px → 332px for `.pane-head`, with the horizontal dimension unchanged to the pixel.
The property to assert is therefore single-line-ness. Comparing an item's height against its siblings'
does not work either — these rows are flex containers with the default `align-items: stretch`, so one
wrapped label grows every sibling to match; counting line boxes with a `Range` is unaffected by that.

**The working-language gate's character range** (`scripts/check-lang.mjs`) covers CJK punctuation and
fullwidth forms as well as ideographs. The ideograph range alone missed a real defect: the fork banner
hard-coded `《 》` in a component, so all six UIs rendered a Chinese book-title mark — Japanese quoting
the same title two different ways, since `ja.ts` already used `『 』` — while the gate stayed green,
because U+300A sits below U+4E00.

**The gate's exemptions are predicates, never counts (settled 2026-08-10).** Each states what *shape* of
Chinese a set of files may contain — "cited inside a literal or a quoting span, never written as prose",
"only a language's own name", "mockup content but not the tooling beside it".

The first design used an exact permitted line count per entry, and it was wrong in a way worth recording,
because a count looks like the more rigorous option. It records what happens to be true today rather than
why it is allowed, so in a file that grows it fires on every legitimate change: measured over 40 commits,
the count for `zh.ts` moved 10 times and the one for `ja.ts` 11 times, once per feature that added copy.
A gate that fires on every legitimate change teaches one reflex — bump the number — and that reflex is the
rubber stamp the count existed to prevent, so the mechanism decays into the thing it was built to stop. A
count is blind to substitution as well: remove one permitted line, add one forbidden line, total unchanged.

The predicates are verified to hold in **both** directions, since only one of them is the point of the
change: adding fifty new Chinese values to `zh.ts` (310 → 357 lines) keeps the gate green, while a single
Chinese comment turns it red. `literalRanges` uses the TypeScript compiler rather than a regular expression
— quoting rules are genuinely hard, and the parser already knows them.

One rule, the Chinese and Japanese READMEs, permits everything it matches and can never go red. That is the
honest answer for a localisation rather than an oversight: there is no shape to distinguish, so its safety
comes from matching two exact filenames instead of from the predicate. Elsewhere, being unable to write a
predicate means the boundary of the exemption has not been worked out, and a number would only paper over
that.
