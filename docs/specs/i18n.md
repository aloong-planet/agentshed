# UI language (i18n)

> Related: ADR-0035 (the language set: Chinese and English) · ADR-0013 (scope boundary) · ADR-0014 (self-built typed i18n layer) · ADR-0015 (structured IPC errors)

## Problem Statement

Every piece of UI copy is hard-coded in Simplified Chinese in the source, so a non-Chinese user
opening the app cannot read a single heading, button, empty state or error notice. The copy is
scattered across the renderer's JSX, errors thrown by the main process, and hand-written date and
number formatting, and no layer of it is replaceable.

## Solution

Support two UI languages, Simplified Chinese and English (ADR-0035), plus "follow system" as **the
default option**. The user can switch at any time from the settings page, and a switch applies to the
whole app immediately, with no restart and no save.

"Follow system" is **a policy, not a snapshot**: while it is selected, the UI follows the macOS
preferred languages, using English when the system language is not supported; choosing a specific
language locks it, and later system language changes no longer affect the UI until the user actively
selects "follow system" again.

Failure information crossing process boundaries becomes a structured form containing no natural
language, and the renderer produces the wording in the current language.

## User Stories

1. As a user whose system prefers Chinese or English, I want the UI to be in that language when I
   open the app, so that I do not have to understand a foreign language first just to find the
   language setting.
2. As someone whose system language is Korean, I want the UI to fall back to English rather than
   Chinese, so that I can at least read an international lingua franca.
3. As a Chinese user on an English system, I want to switch the UI back to Chinese by hand, so that
   the system language does not hold my application language hostage.
4. As a user of any language, I want to see every available language at a glance in settings, each
   written in its own script, so that I can recognise my own language even when the current UI is in
   one I cannot read.
5. As a user, I want each language's English name shown alongside it, so that when I cannot read the
   native script (having switched to Chinese by accident and wanting English back) I have a second
   clue.
6. As a user, I want the whole UI to change immediately on a language switch, including the sidebar
   tooltips and the application menu, so that no half-translated state is left behind.
7. As a keyboard user, I want to switch languages with Tab to focus, arrow keys to select, Enter to
   confirm and Esc to cancel, so that I do not have to use the mouse.
8. As a user, I want my language choice to still be there next time I open the app, so that I do not
   have to set it again every time.
9. As a user, I want failure notices in my language too, so that a foreign language does not appear
   at exactly the moment I most need to understand.
10. As a user, I want dates, times and numbers displayed by my language's conventions, so that I do
    not see American dates in a Chinese UI or Chinese weekday names in an English one.
11. As someone who switches system languages often, I want the UI to follow the system automatically
    when "follow system" is selected, so that I do not have to change it again in the app every time.
12. As someone who always uses one language, I want later system language changes not to affect the
    app once I have chosen a specific language, so that my choice is not quietly overruled by the
    system settings.
13. As a user, I want to see which language "follow system" currently resolves to, so that I do not
    have to guess what that option actually does.
14. As someone who has already chosen a specific language, I want to be able to select "follow system"
    again, so that the decision is reversible rather than one-way.
15. As a developer, I want a missing translation to fail at compile time, so that I do not find out a
    UI is blank only when a user switches to that language.
16. As a developer, I want both languages forced to be complete when adding a piece of copy, so
    that there is no "ship first, translate later" window.

## Functional Requirements

### i18n::REQ-001 The supported languages

The UI languages are Simplified Chinese and English (ADR-0035); French, Spanish, Russian and Japanese
were removed before the first release.

- i18n::REQ-001/AC-01: The settings page's language selector offers three options: "follow system"
  first, a divider, then `简体中文` and `English`, each written in its own script with its English name
  beside it.
- i18n::REQ-001/AC-02: Every piece of UI copy — the settings page, failure notices, the application
  menu, dates and numbers — exists in both languages.
- i18n::REQ-001/AC-03: Nothing in the app is in, or names, a removed language: no dictionary, no
  selector option and no code path for French, Spanish, Russian or Japanese remains.

### i18n::REQ-002 Following the system's preferred languages

With the preference on "follow system", the system's preferred-language list resolves to a supported
language.

- i18n::REQ-002/AC-01: The first entry in the list whose primary language subtag is Chinese or English
  decides the language, wherever it sits in the list: `[ja-JP, zh-Hans-CN, en-US]` gives Chinese, and
  `[fr-FR, en-GB]` gives English.
- i18n::REQ-002/AC-02: A list with no Chinese or English entry (`[fr-FR]`, `[ko-KR, ja-JP]`), an empty
  list and a system language query that fails all give English, without an error.

### i18n::REQ-003 A stored preference naming a removed language (direct acceptance)

When the stored language preference names a language that is no longer supported (`fr`, `es`, `ru` or
`ja`), the preference reads as "follow system" and the language resolves as i18n::REQ-002 states. The
other preferences keep their stored values, and no notice is shown.

## Quality Requirements

### i18n::QR-001 Copy fits in both languages

Applies to: the app's fixed-width containers — rows, tabs, pane heads and toolbars whose width does not
grow with their text. One exception: a project's tab row in a window narrower than the default, where its last tabs run
past the window's edge and its Chinese labels wrap, is accepted as it is
([project-detail::REQ-004](project-detail.md)). At the default window that row is held to this requirement.

- i18n::QR-001/AC-01: Measured in both languages, no label or line in such a container is truncated,
  overflows its box or wraps onto a second line.

## Constraints

### i18n::CON-001 The READMEs are Chinese and English (direct acceptance)

Applies to: the repository's READMEs. They are `README.md` (Chinese) and `README.en.md` (English), and no
other localisation exists. Each has a language switcher row linking both, in which exactly one entry,
its own, is bold. The `check:ui` check verifies both: each README links to the other, and the
switcher row has exactly one bold entry (none, and the reader cannot tell which one they are on; more
than one, and a copy-paste missed an edit).

## Failure modes and boundaries

### Startup and deciding the language

The language preference's value domain is `follow system | zh | en`, defaulting to `follow system`.
"Resolution" in the table below happens only when the preference is "follow system".

| Scenario | Expected behaviour |
|---|---|
| First launch (preference = follow system), the first entry in the system's preferred language list is supported | Use that language |
| The first entry is unsupported but a later entry is supported (e.g. `[ko, ja, zh-Hans-CN, en]`) | Take **the first supported one** in list order, i.e. Chinese (i18n::REQ-002/AC-01). **Do not fall straight back to English just because the first entry missed** |
| No supported language anywhere in the list (e.g. `[ko, fr]`) | English (i18n::REQ-002/AC-02) |
| The system returns tags with a region or script (`zh-Hans-CN`, `en-GB`, `pt-BR`) | Match on the primary language subtag: `zh-Hans-CN` → Chinese, `en-GB` → English; `pt-BR` does not match, so continue to the next entry |
| The system language API returns an empty array or throws | English, no crash |
| The preference is a specific language and differs from the system language | Use the preference's language. The system language **plays no part at all** in the resolution |
| The preference file's language field is an invalid value / the wrong type / has been deleted by hand | Degrade to "follow system" (the default value) and take the resolution path; the other preferences (theme and appearance) are unaffected |
| The preference file's language field names a removed language (`fr`, `es`, `ru`, `ja`), as a development machine's file may | The same as any invalid value: "follow system", resolved from the system list, the other preferences unaffected, no notice (i18n::REQ-003) |
| The whole preference file is corrupt and unparseable | Every preference reverts to its default, so the language is "follow system". Consistent with the existing theme's degradation behaviour |
| The preference file exists and cannot be read (a permission or I/O error, a directory at its path) | Every preference reads as its default, so the language is "follow system", and automatic update checks read as off ([app-update](app-update.md) A3a). The file is kept as it is: see Preference persistence |
| The settings directory cannot be written at launch (read-only, or its disk full) | The app cannot start. A native dialog names the directory and says so, then the app exits non-zero: see The launch dialog |
| The first frame, before the preferences have been read | Must not render a default language first and then jump (FOUC). The language has to be decided before the first frame |

### The dynamics of "follow system"

| Scenario | Expected behaviour |
|---|---|
| The preference is "follow system" and the user changes the macOS preferred languages while the app is running | The UI should change with it. If it cannot be live, it must at least take effect on the next launch, and must never stay stuck in the old language incorrectly |
| The preference is a specific language and the user changes the macOS preferred languages | The UI **does not change**. Measured across every system language configuration |
| Switching from a specific language back to "follow system" | Re-resolve from the current system language and apply immediately, without keeping the previously locked language |
| The preference is "follow system" and the system language goes from supported to unsupported | Fall back to English rather than staying on the last resolved language |
| The two "follow system" settings, UI language and appearance, coexisting | They do not interfere: changing the system language affects only the language, changing the system appearance affects only light/dark. The two are structurally identical but independent preferences, see [appearance](appearance.md) sequence B |

### Switching languages

| Scenario | Expected behaviour |
|---|---|
| Switching to the currently selected option (including re-selecting "follow system") | A no-op, with no notice |
| The notice wording when "follow system" is selected | It must state the current resolution ("set to follow system · currently X"), not just "switched to follow system" — the user cannot tell which language that is |
| An asynchronous scan or load is in flight when the language is switched | The in-flight operation is not interrupted; its completion notice uses the **new** language |
| An error is on screen when the language is switched | An error on a page or in a turn re-renders in the new language (it is held as a code plus parameters, not as a finished sentence). A toast keeps its finished sentence until it goes, at most 3.2 seconds later |
| Writing the language to the preference file fails (full or read-only disk) | The UI language and the application menu still switch (an optimistic update), with a separate failure notice in the language just switched to: it names the language and says the choice stays in effect until the app restarts, then goes back. It never carries the system error, the channel or a path. The other four preferences fail the same way: one notice naming the preference, the choice in effect, and the value on disk back at the next launch |
| A preference write is in flight when the language is switched, and it fails | Its failure notice uses the new language: the notice is worded when the failure arrives, in the language on screen then |
| A preference write fails, and a later one succeeds once the disk has recovered | The store writes its whole record, so the earlier choice is saved too and stays after a restart. The notice's "goes back" holds while no later save succeeds |
| A preference is chosen while the preference file cannot be read | Its save fails and the same notice shows, naming that preference. The choice is in effect until the app restarts. No save succeeds in this run, even if the file becomes readable, since memory holds defaults and not what the file holds. The next launch that can read the file uses it |
| Switching several times in rapid succession | The last one wins, with no intermediate language left behind |

### The dropdown selector

| Scenario | Expected behaviour |
|---|---|
| The settings page scrolls and the page is scrolled while the overlay is open | The overlay closes — it is viewport-positioned, so a scrolled trigger leaves it floating out of place. This follows the floating-layer invariant in AGENTS.md |
| The trigger is at the bottom of the viewport with insufficient space below | The overlay opens upwards and is not clipped by the viewport |
| Clicking elsewhere on the page while the overlay is open | Closes, selecting nothing |
| Pressing Esc while the overlay is open | Closes without changing the language, and focus returns to the trigger |
| Opening the overlay from the keyboard (↓ or Enter) | The highlight **stays on the currently selected item**, without moving an extra step because of the key that opened it |
| Continuing to press an arrow key past the first or last item | Cycles to the other end among the **three** items (follow system + two languages). The divider takes no slot and cannot be focused |
| The secondary text of the "follow system" item | Shows the name of the currently resolved language, updating as the system language changes; it is not static copy |
| Highlighting an item from the keyboard and closing without pressing Enter | The language does not change (highlighting is not selecting) |
| The window is resized while the overlay is open | Repositions to the trigger rather than staying at its old coordinates |
| Opening the settings entry at the foot of the rail | The settings page opens with "Language" as its first section, above "Appearance" |

### The copy itself

| Scenario | Expected behaviour |
|---|---|
| A language is missing a piece of copy | Fails at compile time, never reaching runtime |
| A source-language (zh) value is replaced by text in another language | Every zh value must contain a Chinese character; the few that are correct without one (product terms kept in English, a BCP 47 tag, punctuation-only templates) are pinned to their exact value |
| Copy still cannot be found at runtime (theoretically unreachable) | Fall back to English and warn; never render blank and never display the key name |
| Displaying a quantity in English | Choose the word by English's plural rules (one / other), with no "number + fixed word" concatenation |
| A quantity of 0 | English uses the plural ("0 sessions"), with no special-casing |
| A count next to a noun the source language marks with a counter word (`${n} 条`) | The counter is part of the meaning, not punctuation. Dropping it leaves a bare numeral wedged between two unrelated words with nothing to say what it counts |
| A fixed-width container | No truncation, no overflow **and no wrapping onto a second line**, in either language, with the one exception that i18n::QR-001 states. See the measured note at the end of this document: the rows at risk here wrap rather than clip |
| Punctuation that belongs to the language (quotation marks around a session title) | Comes from the dictionary, never hard-coded in a component. Chinese `《 》` and English `“ ”` are copy, and the same title must be quoted the same way everywhere it appears in one language |
| The UI language differing from the content language (browsing a Chinese session in the English UI) | Content displays as written and is not translated; only the surrounding UI changes with the language |

### Number and time formats

| Scenario | Expected behaviour |
|---|---|
| Relative times (today / yesterday / N days ago) | Expressed in the current language, with no hard-coded Chinese words |
| Weekday and month names | In the current language, not from a hard-coded Chinese array |
| Large number grouping separators | Follow the current language, with no single locale hard-coded. Chinese and English both group as 1,234, so on screen the two cannot be told apart |
| A month/day label | Chinese and English order it alike (8/4), so on screen the two cannot be told apart |
| A value of NaN / Infinity / negative | Do not throw and do not display "NaN"; give a stable degraded representation |
| Byte sizes and durations | The number is formatted by language; the unit symbols (KB / MB / ms) are not translated |

### What imported content can do

i18n adds no new content render sites of its own, but it changes existing render sites' **content
sources**, so each needs its boundary drawn:

- **Error parameter interpolation**: a structured error's parameters (paths, filenames, indices) come
  from the filesystem and user data, and splicing them into wording must go through the same escaping
  as the existing rendering — not bypassed on the grounds that "this is our own error copy".
- **Displaying language names**: the language names are fixed constants, do not come from external
  input, and are not an injection surface.
- **The application menu**: menu item copy comes from the i18n dictionaries (fixed constants). The menu
  is a native main-process control and does not accept arbitrary strings passed in from the renderer.
- **Existing content render sites (sessions, memories, artifacts) are outside this change surface**:
  they render agent-generated content, whose link destinations and sanitising boundaries are already
  constrained by existing invariants, and i18n neither relaxes nor tightens them.

## Implementation Decisions

### The shape of the i18n layer (see ADR-0014)

- Simplified Chinese is the source language and the single source of truth. English aligns to it
  **entry by entry** in the type system, and one missing entry fails typecheck.
- `as const` on the source language narrows the values to literal types, so English cannot reuse
  that type directly; a type mapping is needed that widens leaf values to `string` while preserving
  the completeness of the key set.
- Copy carrying a quantity or an interpolation is expressed as a **function** (parameters in, string
  out), not as a template string concatenated at the call site.
- Plurals call the platform's built-in `Intl.PluralRules` rather than a hand-rolled rule table, with
  the bare language code as the locale tag; CLDR keys plural rules off the primary subtag, so this
  agrees with any full tag for the same language.
- The copy layer is pure data plus pure functions with no React dependency, shared by the main process
  and the renderer.

### Language preference and effective language (two concepts, not to be merged)

- **The language preference** is the persisted user choice, valued `follow system | zh | en`,
  defaulting to "follow system".
- **The effective language** is the language the UI is actually using right now, always Chinese or
  English, derived from the preference: a specific preference is taken as is, and "follow system"
  resolves the system language.
- **Removing a language removes it from the value domain, and nothing else is needed**: a stored
  preference naming it is then an invalid value and degrades like any other (i18n::REQ-003), so there is
  no migration step. No installation existed when French, Spanish, Russian and Japanese were removed;
  only a development machine can hold such a value.
- The two **must not be merged into one field**. Storing the resolution directly into the preference
  would degrade "follow system" into a one-off snapshot — the user changes the system language and the
  app stays on the language resolved back then, with no way left to distinguish "they chose follow
  system" from "they chose that language by hand".

### Language resolution

- The system language comes from `app.getPreferredSystemLanguages()` (which returns a **list** in
  priority order). **Not** `getLocale()` / `getSystemLocale()` — Electron 43's type definitions state
  in both of their docs that the former is what to use for the user's language; the latter two describe
  the regional format (numbers/dates/currency), which is not the same thing as language.
- Matching rule: iterate the list, compare each entry's primary language subtag against the supported
  set, and the first hit wins; fall back to English if none hit. **Iterate the whole list**, not just
  the first entry.
- Resolution is a pure function (language list → effective language), decoupled from preference
  storage, which makes all of the boundaries above unit-testable.
- The language must be decided before the window's content renders, to avoid a first-frame language
  jump.

### The main process emits no natural language (see ADR-0016)

- The constraint widens from "failures crossing IPC" to "all user-facing natural language crossing
  IPC": placeholder and degraded text, truncation markers, advisory copy, quantifiers in configuration
  summaries, and the language-varying entries in display-name tables all become structured signals sent
  by the main process (a code + parameters / `null` / a boolean / a count), with all sentence
  composition happening in the renderer.
- The criterion is executable: a whole-repository Chinese literal search over `src/main`,
  `src/shared` and `src/preload` (**with `grep -a`**, since `token-stats.ts` contains NUL bytes and
  plain grep silently skips it) leaves only developer logs that **never reach the UI** (`console.*`).
- The working-language check (`scripts/check-lang.mjs`) keeps Chinese out of the repository except
  where it is permitted. Its character range covers CJK punctuation and fullwidth forms as well as
  ideographs, so a hard-coded `《 》` in a component is caught. Its exemptions are predicates on the
  shape of the Chinese a set of files may contain — "cited inside a literal or a quoting span, never
  written as prose", "only a language's own name", "mockup content but not the tooling beside it" —
  never an exact permitted line count: adding many Chinese values to the zh dictionary keeps it
  green, while a single Chinese comment turns it red. The Chinese README permits everything it
  matches, because it is matched by one exact filename.
- Truncated text travels as the text plus a flag saying whether it was truncated, and a failure on a
  data field is structured the same way. **"No value here" and "the value is legitimately an empty
  string" must be distinguished in the types**, or the renderer's placeholder fallback will clobber
  a legitimate empty value.

### Structured errors (see ADR-0015)

- Failures crossing IPC travel as an error code plus parameters, containing no natural language. The
  error code enum and the parameter types are defined once and shared by the main process and the
  renderer (ADR-0001's single type source convention).
- **The carrier format**: the code and parameters are **serialised into the Error's message** behind
  the fixed marker prefix `agentshed-error:`, and decoding locates the payload by that marker in the
  string. Both more natural approaches are **unworkable** — when an Error crosses IPC in Electron
  its custom properties are all lost (only `message` / `stack` survive), so `e.code = …` never
  reaches the other side; and the message is wrapped in an `Error invoking remote method '…': Error:
  …` prefix, so `JSON.parse(message)` cannot extract it either. A handler error the main process
  logs itself carries Electron's own `Error occurred in handler` prefix instead; the marker is common
  to every cross-process failure and does not depend on either prefix. When the payload cannot be decoded,
  always **degrade to displaying it as is** (without throwing), which serves both the migration
  period's coexistence and avoids "erroring while reporting an error".
- **Error parameters may only take language-independent values**: identifiers (channel names, field
  names), paths and numbers. Never finished wording — that is precisely what this protocol exists to
  eliminate. A system's or a parser's text is finished wording, so no parameter is filled from a caught
  error: the code's sentence states the failure, and a path stays where it tells the user what to fix.
- **Unknown error codes are not passed through**: decoding validates that the code is in the enum, and
  anything else is displayed as an old-style error as is. Passing it through would leave the renderer
  with no wording and a blank display, and blank is worse than one ugly line of original text.
- **The renderer keeps a "display as is if it will not decode" fallback, and it is permanent**.
  Since the protocol closed no **cross-process producer** throws a sentence, but this path still has
  entry points: the renderer's own TypeErrors and anything a third-party library throws **will never
  have an error code**, and a system error a main-process handler lets through uncaught arrives as
  its raw message. A failed preference write and a failed session read carry codes. The one known
  handler left is listing a skill package's files: only the file disappearing between the resolver's
  check and the listing's, within one synchronous run, reaches it, and that is accepted. So this
  branch is "**the last display guarantee for non-protocol exceptions**", and it stays. The
  acceptance criterion for closing the protocol is not "this code is gone" but **no Chinese
  whole-sentence error crossing a process boundary anywhere in the repository** — the former is
  unreachable and harmful, the latter is searchable and re-checkable.
- The sentences of a side's registry, a failed skill copy or delete, a subagent's toml and a session
  file that cannot be read change copy only: the side card's error line, the notices, the subagent's
  detail line, the session page's error state and the in-turn note keep their forms, and no state is
  added.
- **A new error code must come with its wording, guaranteed by typecheck**: the code → wording
  dispatch is a switch with a `never` assertion at the end, so an unhandled code fails compilation.
- Branching on error semantics is done on the error code. A data field that carries a failure gives
  it a language-independent failure category, and branching is on that category; the detail already
  in the field is display copy, whose wording moves to the renderer with the rest of the display
  copy.
- **The renderer gets the current language from context**: error render sites are scattered across
  the session page, the plugin list and the skill expansion blocks, so passing it down as a prop
  would have to thread through intermediate components with no stake in it; and the spec requires an
  on-screen error to **re-render** in the new language, which a module-level variable cannot do
  since changing it triggers no re-render. So errors are held as a code plus parameters and composed
  into sentences at render time.
- The contract validation layer's failure reasons are included too, with no source-language text
  retained.

### Preference persistence

- Language is one of the app's own preferences alongside the theme, stored with an atomic write and
  a three-tier degradation strategy. A failed write leaves no temporary file in the directory,
  whichever step failed.
- What is persisted is **the preference** (including the `follow system` value), not the resolved
  effective language.
- An invalid single preference degrades only itself and does not affect the others (following the
  existing "degradation may only hurt itself" invariant).
- A file that reads and does not parse is treated as corrupt: every field degrades, and the next
  save replaces it. A file that exists and cannot be read is not corrupt: it may hold everything the
  user chose, so no save replaces it in this run, the same mistake ADR-0039 corrects for the usage
  archive.
- A file readable at launch that stops being readable later is replaced by the next save, from memory, which
  holds the whole record ([token-stats](token-stats.md) C23's rule).

### The application menu

- Electron's default menu is localised by the system language, so the app installs a custom menu whose
  copy comes from i18n and follows the in-app language.
- The structure follows the standard macOS menu set, plus entry points into in-app features:
  settings (⌘,), "Check for Updates…" ([app-update](app-update.md) `app-update::REQ-005`) and, in
  the Edit menu, "Search Sessions…" with ⌘⇧F ([global-search](global-search.md)
  `global-search::US-004/AC-02`). ⌘R belongs to the platform reload role.
- The menu has to be rebuilt after a language switch, not constructed once at startup. That includes a
  switch whose save failed: the language is in effect until the app restarts, and the menu stays with the
  window.

### The launch dialog

- A launch refused the single-instance lock tries the write the lock makes, a symbolic link in the settings
  directory, because the runtime's answer does not say why it refused. Where that fails the app shows a
  native error dialog and exits with code 1; where it succeeds the app exits with code 0 and nothing shown,
  as a second instance. The link's name carries the process id, and it is gone before the answer is given.
  Measured on a directory at mode 555 and on full APFS and HFS+ volumes, where it fails as the lock does.
- The dialog's copy comes from the dictionaries, as the menu's does: it names the directory, says the app
  cannot start because it cannot write there, for example because it is read-only or the disk is full, and
  states no system error, which goes to the log. The language is the stored one, or the system's when the
  preference file gives none, including when it cannot be read.
- It is shown once ready has come, with a 3-second bound. Shown while the module loads, it looks the same and
  takes the foreground the same but is missing from the accessibility tree. On macOS ready never arrives while
  a first instance is running, writable directory or not, so without the bound that launch would run on with
  nothing on screen; at the bound the dialog is in the tree without it. All measured 2026-11-05.
- Under `AGENTSHED_NO_FOREGROUND` the sentence goes to stderr instead of a dialog, on every platform
  and with the same timing, because a modal dialog waits for a click nobody makes.
- **A first instance running, the directory since unwritable**: a click on the icon of a running app starts no
  second process and brings it forward, measured with `open`, so this takes `open -n` or running the binary. The
  runtime tells the first to take focus before refusing, and the second launch then shows the dialog as well, since
  a write is all it can try. What it says is true of that launch. Started from a shell, the dialog comes up without
  taking the foreground from an active first instance, which keeps focus. Started with `open -n` from another application, the dialog comes to
  the front and closing it returns to that application; the same launch with the directory writable does not bring
  the first instance forward either. See `app-update` G5a.
- **A refusal with the directory writable reads as a second instance** and exits silently. The one such case
  measured on macOS is a directory at the lock's path. These were measured and do get the lock: a lock naming
  another machine, a stale lock, a lock naming a live process of another application, a regular file at the
  lock's path, and `TMPDIR` pointing nowhere or read-only. Any other cause would also be silent.
- The app does not run on without the lock, since two instances writing one store is what the lock prevents,
  and offers no reduced mode without its settings directory. A check of the directory at any time after launch
  is not this: token-stats C4 covers scans, and failed saves have their notice.

### UI (conclusions; the form is in the prototype gate below)

- The settings page gains a "Language" section, **placed before "Appearance"** — it determines how the
  rest of the page reads.
- The selector's form is "label + dropdown trigger", opening into an overlay list of **three**
  items: "follow system" first, a divider, then the two specific languages. The divider expresses
  that the two are different in kind — the former is a policy, the latter are values.
- Each item has its primary name on the left (a specific language written in its own script) and
  secondary text on the right, with the current item ticked and highlighted on the right. **The
  secondary text slot of "follow system" holds the currently resolved language name**, in the same slot
  where specific languages hold their English name, so the user can see at a glance what that option
  currently equals.
- With the preference on "follow system" the trigger shows both the policy name and the resolution
  (primary + secondary); with a specific language it shows only that language's native name.
- The overlay **must be positioned outside the settings page's scroll container**. Measured: the
  settings page container is `overflow: auto`, and an ordinary absolutely positioned element of the
  same size inside it gets clipped.
- The overlay's right edge aligns with the trigger's right edge, opening downwards by default and
  upwards when there is not enough space below.
- The new dropdown arrow and the selected tick use **inline SVG**, not characters.
- The overlay's shadow needs a new theme variable, which must be given a value in all six variable
  blocks (3 themes × light/dark), with a higher alpha in dark than in light to be visible.

### Existing shapes explicitly not changed

- The `Provider` and `TrendMode` types once used Chinese literals as runtime values (`'其他'`,
  `'合计'`) and have been **sanitised** into language-independent identifiers (`other` / `total`).
  **It has been verified that these two values were never persisted**: the usage archive's row
  structure stores only the raw model string, the token metering cache's entries likewise store only
  the raw model string (the provider is derived live from the model name every time), and they do not
  appear in the preference file either. So the rename has zero impact on existing user data.
- **Value and display name are separated**: after sanitisation, the UI text comes from a
  display-name table kept apart from the values. The three vendor names and Claude / Codex are
  proper nouns common to every language, so only `other` and `total` need to vary with the UI
  language.
- The per-provider breakdown of usage is keyed by the provider identifier (including `other`), not
  by a free string: the producer and the consumer must agree on every key, because a key one side
  writes and the other does not read makes the segments disappear while the values and bar heights
  stay correct. Whether an unrecognised model's volume reaches a segment at all is part of that
  agreement.
- A search box's placeholder carries copy only, with no icon character glued into the string, or the
  icon would be carried into every language dictionary.

## Out of Scope

- **Arabic and RTL layout**: see ADR-0013. This product makes no RTL commitment, and the CSS keeps
  physical properties rather than converting to logical ones.
- **Multilingual engineering artifacts under `docs/`**: specs / ADR / features / postmortems / ops are
  English only (ADR-0017). The READMEs are the only documents in both languages.
- **French, Spanish, Russian, Japanese, or any language beyond Chinese and English**: removed before
  the first release (ADR-0035). A system preferring one of them gets English (i18n::REQ-002/AC-02).
- **Localising the application name and window title**: Agentshed stays the same in every language as
  a brand name.
- **Converting the existing character icons to SVG**: this round only constrains **new** icon slots
  to follow the inline SVG convention.
- **Translating agent-generated content**: sessions, memories and artifacts display as written.
- **Finer-grained language selection**: no regional variants (no zh-TW / en-GB / pt-BR), and no
  per-project or per-view language.
- **Outsourced translation and online translation platform integration**: copy lives in TS modules and
  is not exported as JSON/PO for external translators to edit.
- **Writing to the agent configuration**: the language choice is stored only in the app's own preference
  file; nothing is written to any agent's configuration.

## Further Notes

Which language is longest differs between short labels and prose paragraphs, so a fixed-width
container is measured in every language, never only in the one assumed longest.

Over-long copy does not burst its container horizontally: tabs shrink to fit by wrapping their
labels, the page does not scroll horizontally, and an over-long label neither clips nor overflows
its box. What happens instead is that the label **wraps and the row grows vertically**, with the
horizontal dimension unchanged. The one place where no label can break further is a project's tab
row at the minimum window, where its tabs run past the window's edge (the accepted boundary in
[project-detail::REQ-004](project-detail.md)).
