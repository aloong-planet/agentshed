## Runnability

**R1 (bug, fixed): a state landing while the hero's download block is above the view moved what the visitor saw.**
The rule decided "the hero is in view" by its bottom being below the window's top. The visible area starts below
the 58px sticky header, and the part that changes is the hero's download block, not the whole hero, so whenever
the hero's bottom was in the window but the block was not (a visitor reading the top of the features section, a
place restored there after a language switch), the late state pushed everything below by the block's growth.
Measured on the old rule with the test state landing after a switch: the features title moved 33.2px with the
hero's bottom at 20, 57, 120 and 400px, without scroll anchoring (as in a browser that has none); with Chrome's
anchoring at 20px still. Fixed: the change is compensated whenever the block's bottom is at or above the
header's bottom. The browser measurement now covers the hero's bottom at nine positions, with and without
anchoring, reaching both branches (the block above the view; in view, where it changes in view and the page does
not scroll), all passing. Two mutations show the checks fail on each half of the rule: the old rule (5 failures,
exactly the positions it gets wrong) and the view starting at the window's top instead of below the header (2
failures, the block hidden under the header) ([keep-place-mutations.txt](evidence/ticket-238/keep-place-mutations.txt)).
Fault escape surface: not an error path; a visible displacement against landing-page Failure A7 and
REQ-004/AC-07, so fixed now.

Class-level form: "a change applied above the visitor's view moves what they see". Every place a state changes
the page: the hero's download block (R1) and the download section's line and buttons. The section: not
reachable, checked. Its change grows the section by at most 22px (400px wide), and for the change to be above
the view the view would have to start below the section, in the footer, which needs the page scrolled further
than its end allows at any window taller than the section and the footer together (measured: the section 335 to
407px in the list state, the footer 78px; about 510px at most with the growth). In a shorter
window, at the page's very end, the footer's links would move by those 22px; left as is (self only: the footer).

Other paths:

- The page's states: served in the list state; the reads run once after load; a state other than the list is
  applied once, in place. No re-read, no timer left behind (each read's time limit is cleared when it answers,
  body included).
- Every way a read can fail ends in a valid page: a rejected or aborted fetch, a time-out, a non-200, a body that
  is not JSON or not the right shape → the next source, then the list state as served. An exception elsewhere is
  caught at the entry and leaves the list state. Measured live: from an origin the download host does not allow,
  the pointer read fails on CORS, GitHub answers `[]`, and the page stays in the list state (Failures A5, A1).
- Fault escape surface: a malformed release entry is passed over and only it (self); a malformed pointer sends the
  page to GitHub (self); nothing escapes to the rest of the page.
- Rate limit: until the first formal release every visit spends one of an address's 60 hourly GitHub requests;
  past the limit the page shows the list state (spec Failure A6).
- GitHub's first hundred releases are read (one page). Only a formal release with more than a hundred newer
  releases on top would be missed, and a formal release is on R2, whose pointer is read first.
- The preview domains Pages gives a branch are not the landing origin, so the pointer's CORS refuses them and they
  fall back to GitHub (measured from a local origin above). Expected; worth knowing when #239 tries a preview.
- Measured: the four states as the spec says, QR-001 at four widths for the three new ones (144 of 144), A7 in
  place, the language switch with a late state, the requests each state makes; section heights identical to the
  confirmed prototype's in each state (211 measurements, [README](evidence/ticket-238/README.md)).

Conclusion: one bug (R1), fixed and measured; no other defect.

## Security

Outside data reaches the page only as a validated version: `\d+.\d+.\d+` with an optional suffix of letters, digits,
dots and hyphens. Every link is built from that version (the mirror's layout for R2, GitHub's URLs for GitHub); the
pointer's DMG URL is accepted only when it is exactly the built one. Release notes, names and URLs from the
answers are never kept. Labels are set as text nodes; a mutation to `insertAdjacentHTML` turns the markup case red
(N14). The page sends no credentials; the reads carry no cookies to other origins (`fetch`'s default). Re-scanned
after R1: the fix reads two fixed selectors and scrolls the window, no new input.

Conclusion: no finding.
